Project purpose and scope 
SimRecrut is a recruitment simulator. A case is one candidate’s CV assessed for one published job. 
We will compare five methods on that case: the Objective Rule, Neutral AI, Biased AI, Standard 
Human and Instructed-Bias Human. In a controlled comparison, we change one background detail, 
keep the qualifications the same and check which results change. 
This specification describes the application, user journey, pages, architecture, storage and 
experiments we plan to build. Accept and Reject are research outcomes, not real hiring decisions. A 
cutoff is the score boundary used to turn a score into Accept or Reject. We still need to build and test 
the system and choose the rule cutoff from pilot cases and model cutoffs from validation data before 
reporting its performance or benefits. 
Member Development responsibility 
MouZheng LI — A Data preparation, models and research analysis 
Zheng LI — B Backend, database, matching and Objective Rule 
YueFan LIU — C Frontend pages and user actions 
YinJI WANG — D CV extraction, integration and deployment 
 
A–D are work slots, not application roles. The live schedule still requires confirmation of task 
allocation and effort. The minimum release includes the complete CV journey, three automated 
results, two primary human-review slots, controlled research comparisons and deletion. Extra models 
for a four-setting research experiment are an optional extension. 
The following sections explain each design through its original Lark diagram and the requirements 
that follow from it. Longer boards retain their complete form; the Candidate flow also has three 
enlarged stage views so its steps can be read in order.

Candidate: from upload to deletion 
A Candidate case moves through three stages: upload and confirmation, automated scoring, then human review and deletion. Follow the stages in order. 
The columns separate the Candidate's actions from Spring Boot, extraction or prediction services, and the records saved in storage. 
Figure 2  The complete Candidate journey 
 
The return arrows are part of the planned behaviour: unreadable files and incomplete facts return to correction, while retries keep saved successes. 
Confirmation must save facts before removing raw files. Scoring needs three saved outputs; human tasks can remain Pending. At deletion, access stops first 
and cleanup continues until it succeeds. 
The normal processing sequence is AWAITING_UPLOAD → UPLOADED → EXTRACTING → REVIEW_REQUIRED → CONFIRMED → 
AUTOMATED_RUNNING → AUTOMATED_COMPLETE. Failure, cancellation and expiry are processing outcomes; human-review and privacy states are 
tracked separately. Unknown is not false, Pending is not Reject, and a service failure never creates a hiring decision. 
Every protected action checks the signed-in user, role, ownership or grant, and current resource state. Repeated publication, confirmation, running, review 
submission or deletion uses an operation key to prevent duplicate work. Reloading a page resumes from server state.

A URL must not silently create a case. Start simulation uses the displayed published job version and 
opens upload only after case creation succeeds. HR requirements and weights are steps in one 
wizard. Published versions are read-only; editing requires a new draft. Weight percentages on screen 
represent stored fractions totalling exactly one. Invalid totals are rejected rather than silently 
normalised. 
The review page holds the CV facts and evidence while the Candidate checks them. Each value 
shows whether it came from the CV, a calculation or a user correction, or whether it is missing or 
conflicting. Short source excerpts and page references are shown where available. We save the 
month used to calculate experience, so retrying later gives the same result. School category, referral, 
gender and ethnicity are kept in a separate optional section. Missing optional values stay Unknown 
and do not block confirmation. The browser never guesses them. 
Poll active extraction or scoring every two seconds. Stop at review, confirmation, completion, failure, 
cancellation, expiry or page exit. At CONFIRMED, wait for Run. A combined confirmation-and-run 
button must first wait for successful confirmation. If Run fails, the confirmed snapshot remains valid. 
Delete clears cached case content and stops polling; a purging case is inaccessible. Clear protected 
facts when leaving the workflow, logging out or losing access. After permissions change or browser 
Back, reload only after the server confirms current access. 
Use these result labels: Objective Fit Score, Neutral ML Acceptance Score, Biased ML Acceptance 
Score, Standard Human Decision and Instructed-Bias Human Decision. Objective uses 0–100; the 
models use 0–1. These scores have different meanings. Human slots have a status and, only after 
submission, a decision and reason. 
Page integration contract 
Browser routes select pages; HTTP endpoints retrieve or change data. New public calls use /api/v1 
exactly once and go to Spring Boot. Existing RuoYi authentication paths keep their existing 
convention. The browser never calls FastAPI, DeepSeek, Redis or MySQL directly. 
Each response contains only fields the current user may see, with code, message, requestId and 
data. Success code is zero. Errors explain the problem without exposing private data and say 
whether a retry is possible. The server checks permissions for every action. Before connecting the 
pages, we must finish requests for reloading HR drafts, checking extraction progress, viewing 
published versions and creating new drafts. Research pages need permitted selection lists, saved 
experiment details, defined metric fields and review assignments. Admin pages need model details, 
release actions, supported retries and audit records. These requests still need implementation.

Private Python FastAPI/Pydantic/PyTorch service validates fixed-version requests

Offline work 
Python, pandas, scikit-learn and PyTorch prepare reviewed data, split people,

Nginx serves the built frontend and forwards /api/v1 unchanged to Spring Boot. Docker Compose 
runs the backend, model service, MySQL and Redis separately. Spring runs a limited number of 
background tasks, while MySQL records queued extraction, assessment and cleanup work. We do 
not need a separate message broker for the initial version. We still need to select and record 
compatible RuoYi, Java/Spring and dependency versions. 
How a request reaches the database 
Vue is the View. A Spring MVC controller receives an HTTP request and returns permitted fields. 
Application services coordinate the action. Business services enforce access, state and version 
rules. Pure domain code calculates matching and the Objective Rule. MyBatis mappers read or 
change rows. This is the application’s Model layer; a neural prediction model is a separate 
component. 
The usual call order is controller → application coordinator → business service interface → service 
implementation → mapper → MySQL. Controllers receive requests. The interface defines the 
service’s operations; its implementation checks rules and owns the short database save. Mappers 
handle SQL. The matching and Objective Rule calculations stay independent of HTTP, SQL and 
research attributes. Adapters connect OCR, DeepSeek and FastAPI, check responses and turn 
failures into clear errors. PDFBox is used directly. Interfaces are added where a component needs to 
be replaceable; MyBatis provides the mapper implementations. 
Database saves use short transactions, meaning related changes succeed or fail together. The 
backend releases database locks before waiting for OCR, DeepSeek, prediction or file operations. 
Before saving a prediction, it checks the returned case/request IDs, model and input versions, score 
ranges and decisions. It also checks that deletion has not started. FastAPI returns predictions; the 
backend saves them. 
Repository organisation 
frontend/src contains pages, routes, shared UI and API modules. The backend Java root groups 
controllers, application/business/domain code, entities, mappers and adapters; resources contain 
mapper SQL and migrations, with separate tests. ml/service is inference only; ml/training, 
ml/evaluation, schemas and tests are offline work. scripts contains cleaning, pairing and validation; 
datasets contains raw/clean data, manifests and shared reference cases. model_artifacts stores 
immutable versioned packages. runtime/cases stores restricted live workspaces excluded from Git 
and the public web. docs holds specifications, protocols and release instructions.

Of the 65 links, 39 prevent deletion while other records still refer to the item, 22 require the service to 
delete dependent records, and four clear optional account links. Used jobs and model/protocol 
versions are archived or retired. Services check linked records and save changes in the same short 
transaction. Creation and deletion lock records in the same agreed order, preventing a simultaneous 
insert from leaving a record with a missing parent. 
The planned schema keeps 36 primary keys, 34 additional unique constraints, 80 field checks and 28 
extra indexes for linked-record lookups. We still need to apply and test the migrations. Further rules 
must prevent duplicate review assignments and experiment subjects, keep one primary human result 
per case/condition and one active core model of each type, and check training membership and 
splits. They must also prevent duplicate generated samples and define how metrics and deletion 
receipts are safely updated. A submitted review needs a decision, reason and time. Repeated 
requests must not create duplicate metric records or deletion receipts. 
Temporary files and deletion 
Live PDF, extracted text, redacted text and review drafts stay in a restricted case workspace. The 
initial design uses server storage; an S3-style private store can replace it behind the workspace 
component if access and deletion behaviour remain the same. Files are not permanent downloads. 
Offline research data is separate; live uploads never automatically enter training. 
An unconfirmed case expires 24 hours after creation, even if extraction fails. Uploading again does 
not extend that deadline. Confirmation sets a 30-day deadline even if the case is never run. When all 
automated results are saved, the deadline becomes 30 days after that completion. A user can delete 
earlier. We save the confirmed facts before removing raw and intermediate files. If file cleanup fails, it 
is retried while the confirmed facts remain valid. 
Deletion first blocks case access and marks PURGING, meaning cleanup is in progress. It removes 
access grants, stops workers from saving new content and cancels pending reviews. Cleanup 
removes files, caches, facts, research values, matching, automatic results and human reasons. It 
also removes case-linked experiment subjects, variants and results, then removes or recalculates 
affected metrics. Only after cleanup succeeds is the case deleted. We keep a receipt showing 
deletion without retaining case content. Failed cleanup stays blocked and is retried. A case is still 
linked to an account even after its name is removed.

Repeat requests, recovery and precision 
Each repeatable action has a request key linked to the user, action and target record. The server 
saves a fingerprint of the submitted data, called a request hash. If the same completed request is 
sent again, the server checks current access and returns the saved result. Different data under the 
same key is rejected. These records normally expire after 24 hours. Saved responses must be 
cleared when needed so they cannot bring deleted case content back. 
Starting Run saves its task, fixed model versions, running state and repeat-request response 
together before prediction. Repeated Run or restart therefore resumes one saved task. MySQL 
records which background worker is handling each task. A worker is a process that performs 
extraction, scoring or cleanup. A worker claims a task in one database transaction, so only one 
current claim is valid. It receives a unique task token and time limit, and sends regular updates to 
keep its claim valid. Work starts after the task is saved; a separate check also finds saved tasks that 
have not started. After a restart or an expired claim, another worker resumes the unfinished stage 
with the same saved versions. An old worker, or one stopped by deletion, cannot save results. 
Retries keep successful outputs. A model failure is recorded as an error, with no invented score or 
Reject result. 
Matches, HR weights, contributions and the rule cutoff use seven decimal places with HALF_UP 
rounding. Bias adjustments use eight places. Model scores keep their floating-point precision and 
must be valid finite numbers; only the displayed values are rounded. Java and Python use the same 
reference cases: fix the matches, round each weighted contribution in the same way, sum them and 
compare with the saved cutoff. Public IDs are ULID strings, not numbers. Timestamps use UTC with 
milliseconds. Rounded screen values are never reused for scoring. 
CV extraction and fact confirmation 
The upload accepts one PDF of at most 10 MB and 20 pages, with no password or encryption. The 
server validates its actual content. PDFBox reads embedded text first. Only when that text is 
unusable does Tesseract 5 recognise characters from page images, using English and French 
language data. 
Before external extraction, the backend removes direct identifiers such as name, email, phone and 
exact address. DeepSeek converts the redacted text into facts about skills, relevant dates, education, 
languages and projects. It is not asked to score, decide Accept/Reject or infer demographics. The 
backend validates structure, field types and allowed values and records evidence and extraction 
versions. 
The planned external limits are five seconds to connect and 20 seconds to read, with one retry for a 
temporary transport/service failure and one structured-output repair attempt. If extraction still fails, 
show a retry or replacement action. Candidate checks the draft; unresolved facts required by active 
job criteria block confirmation and scoring. Optional research unknowns remain unknown. 
Confirmation and assessment are different actions. After confirmation, the saved professional facts 
cannot be edited. Changed professional information requires a new case. Case creation already 
records the fixed published job and protocol references. Run keeps those rule/schema references 
and freezes the selected Neutral and Biased model versions. Historical results and retries use the 
same recorded inputs. 
DeepSeek is isolated behind a replaceable extraction client. A rule/template or local extraction tool 
can be tested against the same required fields and source evidence. We will compare field accuracy, 
errors, processing time, memory and external calls before choosing a replacement. Reading 
embedded text first and reusing unchanged extraction/models can reduce unnecessary processing, 
but we have not measured energy savings.

An inactive category is not assessed, so its match and weight are zero. Every active calculation 
needs a valid requirement set or target: we cannot divide by zero. Active weights cannot be negative 
and must add up to one. At least one category must be active. An optional qualification counts only 
when HR includes it. If a needed fact is unresolved, the Candidate must review it before scoring. 
S = Σ(weight × match)     displayed fit = 100 × S 
Objective Accept ⇔ every mandatory check passes and S ≥ T_rule 
If there are no mandatory conditions, this check passes. An unresolved mandatory condition blocks 
scoring. The same inputs and settings give the same rule result. People still choose the matching 
rules and cutoff. 
Calibrating the rule cutoff 
Use at least 20 development candidate-job cases and two independent reviewers who do not see the 
score. Resolve disagreements and keep these profiles outside the final test. Try cutoffs between 
distinct scores plus zero and one. Maximise balanced accuracy, then macro-F1, then choose the 
middle of a tied interval. Both Accept and Reject must be represented; undefined metrics require a 
better pilot. Freeze the cutoff before label generation and check a five-percentage-point window 
around it. 
For example, matches 0.75, 0.50, 1.00, 1.00, 0.50 with weights 0.40, 0.25, 0.15, 0.10, 0.10 give 
contributions 0.300, 0.125, 0.150, 0.100, 0.050: S = 0.725, displayed as 72.5/100. With a passing 
mandatory gate and the illustrative cutoff 0.70, the neutral label is Accept. This cutoff is an example, 
not a calibrated result.

demographic groups. We therefore construct the candidate-job pairs and training labels for our 
experiment.

Neutral input = [u, 16 zeros]     Biased input = [u, z]     both have 32 values 
Python creates Neutral’s zero mask: it means information is withheld, not that all categories are 
unknown. Biased receives permitted category values and Python encodes them. Labels, bias effects 
and the biased target score never enter either model’s input. 
The Neutral training label Y_N is the Objective decision. For the Biased label, we add the 
background adjustments defined in the experiment protocol to S. Values below zero become zero; 
values above one become one. Y_B is Accept only when all mandatory checks pass and the 
adjusted score reaches T_rule. Unknown adds no background adjustment and must appear in 
training examples. Each adjustment is part of our experiment, not a claim that one group is generally 
better than another. 
To choose small, medium and large adjustments, we measure how far each training or calibration 
score whose mandatory checks all pass is from the cutoff. We sort these distances and use the 
values at the 25%, 50% and 75% points: the corresponding percentiles. We start the combined 
experiment at medium, then check how often scores reach zero or one and decisions change. If 
background adjustments dominate the professional score, we reduce them before fixing the protocol. 
A hypothetical adjustment of −0.08 changes 0.725 to 0.645, crossing the example cutoff of 0.70 while 
qualifications stay unchanged. 
Network and prediction 
32 inputs → 16 hidden values → ReLU → 10% dropout → 8 hidden values → ReLU → 1 raw output 
→ sigmoid 
Each network has 673 learned parameters and is trained independently. ReLU keeps positive values 
and replaces negative ones with zero; sigmoid converts the raw output to a 0–1 score. Dropout skips 
10% of the first hidden values during training and is off during prediction. HR weights are input 
values; network weights are learned values. 
Neutral and Biased have separate saved cutoffs T_N and T_B, selected on validation data. These 
differ from the rule cutoff that created the labels. A neural model can predict Accept despite a failed 
mandatory check; retain and report that disagreement instead of overwriting it. The acceptance score 
is not a real hiring probability. Logistic regression is a simpler model for comparison.

What the experiments measure 
Report accuracy, balanced accuracy, macro-F1 and a confusion matrix against each model’s own 
labels. Balanced accuracy gives equal weight to recognising Accept and Reject; macro-F1 averages 
the F1 scores for Accept and Reject; each F1 combines precision and recall. Compare both models 
with Y_N as a shared rule reference too. This measures agreement with our constructed rule, not 
real hiring accuracy. 
A controlled pair changes exactly one research factor. Professional facts, job, weights, protocol and 
models stay fixed. Record score differences and the fraction of decisions that flip. Objective and 
Neutral must stay unchanged when their actual inputs do not change. Test unseen job configurations 
and weights separately. 
Use Fairlearn to calculate group metrics and always show the counts used. Selection rate is 
accepted cases divided by all cases in the group. For each group, true-positive rate is accepted 
cases that pass the rule divided by all cases in that group that pass the rule. If a group has no rule-
qualified cases, its TPR is undefined. For Top-K comparisons, state the number K of available places 
and compare the selected group composition with the original pool. One metric or disagreement 
alone does not prove real discrimination or overall fairness.
